# CLAUDE.md

Заметки для будущих сессий по проекту **«Генератор КП по SEO — Qmedia»**.
Подробности для людей — в [README.md](README.md). Здесь — карта кода, доменная логика и
неочевидные грабли, на которые уже наступили.

## Что это

Внутренний инструмент Qmedia: по параметрам проекта считает стоимость SEO по 5 направлениям,
генерирует **PDF** (КП для клиента) и **Excel** (план + расчёт), сохраняет каждую генерацию
JSON-файлом, умеет импортировать JSON и пересчитывать. Ставки/коэффициенты расчёта, списки
работ по направлениям и справочник менеджеров правятся через интерфейс (`/settings`) —
см. «Настройки».

Стек: **Next.js 14 (App Router) + TypeScript + Tailwind**, `@react-pdf/renderer` (PDF),
`exceljs` (Excel), `zod` (валидация), `vitest` (тесты), **Postgres** (Neon/Supabase) через `pg`.

## Команды

```bash
npm run dev     # dev (порт 3000, при занятости — 3001 и т.д.); нужен DATABASE_URL в .env.local
npm run build   # прод-сборка (заодно полная проверка типов)
npm test        # юнит-тесты расчёта (БД не требуется — calc чистый)
npx tsc --noEmit
```

Хранилищу нужен Postgres: задать `DATABASE_URL` в `.env.local` (шаблон — `.env.example`).
Локально проще всего через `Makefile` (поднимает Postgres в Docker + dev-сервер):

```bash
make init      # зависимости + .env.local + контейнер Postgres (seocp-pg)
make dev       # dev-сервер в foreground; make start — фоном; make stop/restart/status/logs
```

`make start` запускает `npm run dev` фоном с `nohup`, PID — в `.dev-server.pid` (gitignored),
логи — `.dev-server.log`; `stop-dev` гасит дерево процессов по PID (через рекурсивный `pgrep`),
`db-stop` делает `docker stop` (данные в томе `seocp-pgdata` сохраняются). Без Docker — обычный
`docker run ... postgres:16-alpine` и ручной `DATABASE_URL`.

## Карта кода

- `lib/seo-config.ts` — ставки и коэффициенты **по умолчанию** (выверено по
  `sources/Расчет SEO.xlsx`) плюс списки опций форм, названия и порядок направлений.
  Числа отсюда — только дефолты: рабочие значения живут в БД (см. `lib/calc-config.ts`).
- `lib/calc-config.ts` — `CalcConfig` (всё, что настраивается через интерфейс),
  `DEFAULT_CALC_CONFIG` (собран из `seo-config.ts`), `mergeCalcConfig` (толерантное чтение
  «сырого» JSON из БД: битое/отсутствующее заменяется дефолтом) и метаданные для формы
  настроек (`COEF_GROUPS` — подписи и пояснения).
- `lib/calc.ts` — чистая функция `calculate(input, directions, config?)`. Логика 1:1 с Excel;
  без третьего аргумента считает по `DEFAULT_CALC_CONFIG` (на этом держится золотой тест).
- `lib/works-catalog.ts` — 5 направлений: ключ, название, цель и работы **по умолчанию**
  (из `sources/Разбивка SEO по блокам работ.md`). Рабочие списки работ живут в БД
  (см. `lib/works-config.ts`); название и цель через интерфейс не меняются.
- `lib/works-config.ts` — `WorksConfig` (`направление → string[]`), `DEFAULT_WORKS_CONFIG`,
  `mergeWorksConfig` (толерантное чтение jsonb: битое/отсутствующее направление берёт
  дефолт, тексты чистятся и дедуплицируются) и `buildWorksCatalog` — каталог для визарда
  (работы из настроек + название/цель из `works-catalog.ts`).
- `lib/company.ts` — фирстиль Qmedia: цвета (`BRAND`, **green-forward**), ассеты (`BRAND_ASSETS`),
  фото (`PHOTOS`), контакты/факты (`COMPANY`), преимущества.
- `lib/storage.ts` — хранилище КП в Postgres (таблица `proposals(id, created_at, data jsonb)`).
  `buildProposal(payload, config)` кладёт в КП снимок настроек (`calcConfig`) и менеджера.
- `lib/settings.ts` — настройки в Postgres (таблица `app_settings(key, data jsonb, updated_at)`),
  три ключа: `calc` (`CalcConfig`), `works` (`WorksConfig`) и `managers` (справочник).
  У читающих функций две версии:
  `getCalcConfig`/`getManagers` (пробрасывают ошибку БД — используются там, где считается и
  сохраняется КП) и `…OrDefault` (откат на дефолты — для рендера страниц).
  Плюс фото менеджеров — таблица `manager_photos` (`getManagerPhoto`/`saveManagerPhoto(s)`/
  `deleteManagerPhoto`); `saveManagers` заодно чистит фото тех, кого в списке не осталось.
- `lib/manager-photos.ts` — фото менеджеров: белый список MIME, потолок размера,
  `parsePhotoDataUrl` (разбор data-URL из формы) и `photoVersion` (отпечаток файла).
  Модуль серверный (`node:crypto`) — в клиентские компоненты не импортировать.
- `lib/qmedia-managers.ts` — синхронизация справочника менеджеров с qmedia.by: парсер
  блока `ul.contact__list` (`parseQmediaManagers`) и слияние с текущим списком
  (`mergeManagersFromSite`). Чистые функции + `fetchQmediaManagers`/`fetchQmediaPhotos`.
- `lib/db.ts` — singleton-пул `pg` по `DATABASE_URL` (Neon/Supabase) + ленивое
  `ensureSchema()` (прогоняет миграции при первом обращении, результат кэшируется
  на процесс). SSL включается автоматически для удалённых хостов, для `localhost` выключен.
- `lib/migrations.ts` — миграции схемы и данных (см. «Миграции»).
- `lib/pdf/ProposalPdf.tsx` — PDF-документ (A4 landscape) по референсу `sources/cp-development.pdf`:
  обложка (фото + зелёный оверлей + белый логотип + Q-watermark), `HeaderBand` (зелёный градиент-
  колонтитул с Q-watermark, `fixed`), подвал. Порядок слайдов — см. «Структура PDF» ниже.
- `lib/pitch.ts` — **тексты презентационных слайдов** (источник — `sources/SEO_CP_SLIDES.md` от
  SEO-отдела). Только контент, без вёрстки; правки относительно исходника перечислены в шапке
  файла (убраны внутренние TODO и пустые пункты, опечатки, сквозная нумерация).
- `lib/xlsx/buildWorkbook.ts` — Excel (листы «Расчёт» и «План работ»). Зелёные шапки/секции,
  жёлтый — только акцент на итоговой строке.
- `app/api/proposals/...` — route handlers (CRUD, import, pdf, xlsx);
  `app/api/settings/calc` и `app/api/settings/works` (GET/PUT/DELETE-сброс),
  `app/api/settings/managers` (GET/PUT), `app/api/settings/managers/[id]/photo`
  (GET-картинка / PUT-загрузить / DELETE) и `app/api/settings/managers/sync`
  (GET-предпросмотр / POST-применить синхронизацию с сайтом).
  Все: `runtime="nodejs"`, `dynamic="force-dynamic"`.
- `components/` — визард (`Wizard`, `StepProject`, `StepDirections`, `StepManager`,
  `StepReview`, `CostPanel`), `ProposalList` и настройки (`SettingsView` — вкладки,
  `SettingsCalc`, `SettingsWorks`, `SettingsManagers`); `ManagerAvatar` — круглое фото
  менеджера и адрес картинки, общий для настроек и шага «Менеджер».
- `app/new/page.tsx` и `app/settings/page.tsx` — серверные страницы: читают настройки из БД
  (расчёт + работы + менеджеры) и передают пропсами в клиентские компоненты (в браузере
  настройки не догружаются).
- `__tests__/calc.test.ts` — **золотой тест** (см. ниже).

## Структура PDF

Продающая логика: сначала подход и направления, потом цена, потом снятие возражений.
Порядок закреплён (менялся по согласованию — не переставлять «заодно»):

1. Обложка
2. Комплексное SEO 2.0 · 3. Почему обычное SEO не работает · 4. Экосистема из 5 типов SEO ·
   5. Путь клиента
6. **Смета** (расчёт)
7…N. **По два листа на направление** (итерация по `proposal.directions`, порядок сметы):
   - *описание* — презентационный слайд из `PITCH_DIRECTIONS` (по `pitchByKey`), плашка
     `DirectionBadge` со сроком из расчёта;
   - *состав работ* — `WorksSlide`: баннер «стоимость в месяц · период · объём» + карточки работ.
N+1. Команда · Project-менеджер · Инструменты · Аналитика · Гарантии · Клиенты
     · Почему Qmedia + контакты (`ADVANTAGES` + `PITCH_WHY`)

Итого ~22 листа при полном каталоге. От расчёта зависят только смета и `WorksSlide`.

- Слайд *описания* показывается **всегда**, даже для выключенного направления (бейдж
  «не входит») — клиент видит весь спектр услуг.
- Слайд *состава работ* — **только при `activeMonths.length > 0`**: расписывать работы,
  которых нет в предложении, незачем.
- `WorksSlide` режет пункт каталога по первому ` — ` (`splitWork`): слева жирный заголовок,
  ниже серое описание. У произвольных работ тире может не быть — тогда весь текст идёт
  заголовком.
- **Крупная цифра в PDF — всегда платёж за месяц, не сумма за срок** (фидбэк отдела продаж
  от 05.08.2026: «17 тыс. за 3 месяца — дорого и страшно, дробить»). Жёлтые плашки сметы
  (`costHighlight`) и слайда работ (`dirCostSum`) показывают месяц; сумма за срок остаётся,
  но обычной строкой: в карточке сметы («Итого за N»), в колонке «За срок» серым и в подписи
  ячейки «Период работ». Помесячные величины берутся из `pricePerMonth`/`fullPricePerMonth`/
  `hoursPerMonth` (`DirectionScheduleCalc`) и `calc.months`, форматируются
  `formatMonthlyMoney/Amount/Hours` (lib/format.ts): месяцы одинаковы → одно число, разные
  → «от N» (детали клиент видит в матрице «Состав по месяцам»).
- Строки «Без скидки в месяц» / «Экономия» в смете показываются помесячно **только когда
  набор направлений одинаков во все месяцы** (`sameEveryMonth`): иначе минимумы по строкам
  пришли бы из разных месяцев и не сходились бы между собой — тогда экономия даётся за срок.
- **Вертикаль листа выбрана впритык — любая правка отступов ломает пагинацию.**
  `s.page.paddingBottom` = 52pt: зелёная черта подвала начинается в 35pt от низа, остальное
  воздух (при 38pt контент слипался с чертой). На этот бюджет подогнаны два самых плотных
  слайда: `WorksSlide` с 11 работами (6 рядов сетки 2×N) и «Аналитика» (формат отчётности —
  3 колонки по 2 пункта, в 2 колонки лист рвётся). Меняешь размеры/отступы — перепроверяй
  числом листов в рендере, а не на глаз.

Общие примитивы слайда в `ProposalPdf.tsx`: `Slide` (каркас: колонтитул + контент +
прижатая к низу полоса + подвал), `Lead`, `Paras`, `Bullets` (маркер `dot`/`check`/`cross`),
`Notes`, `ResultStrip`, `Group`, `NumCircle`.

## Деплой (Docker, своё облако)

Хостинг переезжает с Vercel/Supabase на собственный сервер с Docker. Схема повторяет
CI соседнего проекта qmedia (образы в GHCR, compose на сервере, единый серверный `.env`):

- `docker/Dockerfile` — multi-stage образ приложения: `npm ci` → `next build`
  (**`output: "standalone"`** в `next.config.mjs`) → тонкий runtime `node:22-alpine`.
  Контекст сборки — корень репо (лишнее режет `.dockerignore`). БД на сборке не нужна.
- `docker/docker-compose-server.yml` — серверный стек: `app` (образ из GHCR, порт
  `127.0.0.1:PORT_APP`, наружу — reverse-proxy хоста) + `database` (postgres:16-alpine,
  том `pgdata`). `DATABASE_URL` собирается в compose с `?sslmode=disable` —
  `lib/db.ts` понимает этот флаг и не включает TLS (иначе бы пытался, хост не localhost).
- `.github/workflows/deployment.yml` — деплой на push в `main`/`dev` (environment
  production/development) или вручную: preflight серверного `.env` → юнит-тесты →
  build&push образа в GHCR → дамп БД + запоминание текущего `IMAGE_TAG` → rsync только
  `docker/` → `compose pull` + `up --wait` → health-check → при провале откат на
  предыдущий `IMAGE_TAG`. Код на сервер не синхронизируется — всё в образе.
- Секреты (per-environment): `DEPLOYMENT_HOST/USER/SSH_PRIVATE_KEY/FOLDER`.
  Одноразовый бутстрап сервера: `<DEPLOYMENT_FOLDER>/.env` из `.env.server.example`
  (CI обновляет в нём только `IMAGE_TAG`) + reverse-proxy на `PORT_APP`.
- Отдельного шага миграций в CI нет — их прогоняет `ensureSchema()` лениво при первом
  запросе (см. «Миграции»). Поэтому деплой не зависит от доступности БД в момент выката.
- `keep-supabase-awake.yml` актуален, пока прод-БД на Supabase; после переезда удалить.

### Индексация закрыта

Инструмент внутренний и **авторизации не имеет**, поэтому от поиска закрыт в три слоя —
снимать по отдельности нельзя, каждый закрывает свою дыру:

- `app/robots.ts` → `/robots.txt` с `Disallow: /` — запрещает **обход**, но не индексацию.
- `headers()` в `next.config.mjs` → `X-Robots-Tag: noindex, nofollow, …` на `/:path*` —
  главный слой: запрещает **индексацию** и, в отличие от меты, работает для выгрузок из
  `/api` (PDF/Excel) и статики из `public/`.
- `metadata.robots` в `app/layout.tsx` → `<meta name="robots">` на всех страницах.

**🛑 `Disallow: /` сам по себе от индекса не спасает** — наоборот, он мешает роботу
прочитать `noindex`, и страница может попасть в выдачу по внешней ссылке (без сниппета).
Работает это только в паре с `X-Robots-Tag`, который роботы видят и на закрытых путях,
если всё-таки зашли. Единственная настоящая защита от посторонних — авторизация
(basic auth на reverse-proxy хоста или VPN), robots.txt данные не прячет.

## Миграции

`lib/migrations.ts` — самописный раннер (~50 строк, без зависимостей): массив миграций
`{ id, run(client) }` + журнал `schema_migrations`. Прогоняются лениво из `ensureSchema()`,
никаких CLI и шагов деплоя. Инструмент вроде node-pg-migrate тут дороже: его пришлось бы
тащить в тонкий standalone-образ вместе с файлами миграций и вклинивать шаг между
`compose pull` и `up --wait`.

- **Применённые миграции неизменяемы**: правка/удаление уже выкаченной миграции разведёт
  базы (на проде она отмечена в журнале и не переиграется). Только добавлять следующую.
- **Порядок в массиве = порядок применения**, `id` — `NNNN_смысл`; каждая идёт в своей
  транзакции. Тест в `__tests__/works-config.test.ts` следит за уникальностью и сортировкой
  id.
- **🛑 `CREATE TABLE IF NOT EXISTS` не атомарен.** Два холодных старта одновременно роняли
  друг друга: `duplicate key value violates unique constraint "pg_type_typname_nsp_index"`.
  Поэтому `pg_advisory_lock` берётся **первым**, до создания даже самой `schema_migrations`
  (ловится тестом на двух пулах против чистой БД; прежний `ensureSchema` этой гонке был
  подвержен). SQL всё равно пишем идемпотентным — базы правились руками до появления журнала.
- `0001_init` — `proposals` и `app_settings` (то, что раньше создавал `ensureSchema`);
  `0002_seed_works` — перенос каталога работ из кода в БД (см. «Работы направлений»);
  `0003_manager_photos` — таблица `manager_photos` (см. «Фото менеджеров»).

## Настройки (`/settings`)

Кнопка-шестерёнка в шапке (`app/layout.tsx`). Три вкладки:

- **Данные для расчёта** — весь `CalcConfig`: базовая стоимость, стоимость часа, коэффициенты
  направлений, матрица «какие коэффициенты входят в формулу направления», пакетная скидка
  (триггер + получатели + процент) и все 7 таблиц коэффициентов параметров. Есть сброс
  к дефолтам (`DELETE /api/settings/calc` просто удаляет строку из `app_settings`).
- **Работы направлений** — `WorksConfig`: списки заготовок работ, которые визард предлагает
  отметить. Добавление, правка, удаление и перестановка (↑/↓). См. ниже.
- **Список менеджеров** — фото / Имя Фамилия / специальность / телефон / email. Текстовые
  поля хранятся одним массивом; добавление, правка и удаление сразу отправляют список
  целиком (`PUT`). Фото — отдельной ручкой, см. «Фото менеджеров».
  Пока строки в БД нет, `getManagers()` отдаёт одного менеджера из `COMPANY.manager`.
  Плюс кнопка «Забрать с qmedia.by» — синхронизация с сайтом, см. ниже.

### Работы направлений

Каталог работ переехал из кода в БД (`app_settings`, ключ `works`), в коде остались только
дефолты (`lib/works-catalog.ts` → `DEFAULT_WORKS_CONFIG`).

- **Правится только список работ.** Ключ, название, цель и порядок направлений остаются в
  коде: на них завязаны вёрстка слайдов, порядок сметы и `PITCH_DIRECTIONS`.
- **Текст работы — её идентификатор** в визарде (по нему стоит галочка и собирается
  `DirectionSelection.works`), поэтому `mergeWorksConfig` схлопывает пробелы и **выбрасывает
  дубли**: две одинаковые строки переключались бы одной галочкой и ломали бы React-ключи.
- **Пустой массив ≠ отсутствие настройки.** Направление без ключа в jsonb получает дефолтный
  список, а явно сохранённый `[]` так и остаётся пустым (в визарде — направление без
  заготовок, только ручные работы). Та же логика, что у справочника менеджеров.
- **Порядок работ значим** — это порядок карточек на слайде «Состав работ» и строк в Excel,
  поэтому в настройках есть ↑/↓, а не только добавление/удаление. Помни про пагинацию PDF:
  `WorksSlide` подогнан под 11 работ (см. «Структура PDF») — более длинный список порвёт
  лист. Первое ` — ` в тексте делит пункт на заголовок и описание (`splitWork`).
- **Перенос в БД — миграция `0002_seed_works`**, а не посев на каждом старте: списки из кода
  кладутся в `app_settings` один раз и отмечаются в журнале. Дальше **источник истины — БД**:
  правки `works-catalog.ts` на уже мигрированную базу не попадают (списки правят в
  `/settings`).
- **Сброса к дефолтам у работ намеренно нет** (в отличие от вкладки расчёта): кнопка,
  затирающая вручную выверенные формулировки всего каталога, — лишний способ выстрелить
  себе в ногу. `DELETE /api/settings/works` тоже нет.
- Тесты — `__tests__/works-config.test.ts` (merge, каталог, снимок работ в КП, журнал
  миграций).

### Фото менеджеров

Фото — не поле справочника, а отдельная таблица `manager_photos(manager_id, mime, version,
bytes, updated_at)`; в самом справочнике живёт только производное `Manager.photoVersion`
(отпечаток картинки), которое `getManagers()` подмешивает при чтении, а `saveManagers()`
не сохраняет.

- **Почему не base64 в jsonb.** Справочник читается на каждый рендер `/new` и уезжает в
  браузер пропсами (`Wizard` → `StepManager`). 13 аватарок с сайта — это ~530 КБ, в base64
  ~700 КБ: они висели бы в RSC-payload каждой страницы визарда и перезаписывались бы
  целиком при любой правке имени. Так же и `PUT /api/settings/managers` остаётся лёгким.
- **Адрес картинки — со штампом версии**: `/api/settings/managers/{id}/photo?v={photoVersion}`.
  Ответ отдаётся с `immutable` на год, поэтому без штампа браузер показывал бы старое фото
  после замены. Формируется этот адрес в одном месте — `managerPhotoUrl` в
  `components/ManagerAvatar.tsx` (модуль `lib/manager-photos.ts` серверный, `node:crypto`,
  в клиент его не тянем).
- Показывается фото в двух местах: карточки в настройках и карточки выбора на шаге
  «Менеджер» в визарде (оба через `ManagerAvatar`). В PDF/Excel фото пока не попадает.
- **Файл ужимается в браузере** (`toPhotoDataUrl`): кадр по центру в квадрат 512 px и JPEG
  0.85 — иначе с телефона прилетает несколько мегабайт ради аватарки 48×48. Сервер всё
  равно проверяет MIME и потолок `MAX_PHOTO_BYTES` (1 МБ): клиент — удобство, не защита.
- **Фото сохраняется вторым запросом, после списка.** Порядок принципиален: `saveManagers`
  чистит фото, чьих менеджеров в списке нет, — залей картинку раньше, и её тут же снесло бы
  как ничью. Тот же порядок в синхронизации (`saveManagers` → `saveManagerPhotos`).
- Удаление менеджера фото подчищает автоматически (внешнего ключа нет — справочник в jsonb).

### Синхронизация менеджеров с qmedia.by

Главный источник по менеджерам — блок «Персональные менеджеры» (`ul.contact__list`) на
`https://www.qmedia.by/kontakty.html` (имя, должность, телефон, email — мессенджеры не
берём). `lib/qmedia-managers.ts` его качает и разбирает,
`app/api/settings/managers/sync` отдаёт план (`GET`, ничего не пишет) и применяет его
(`POST`, план пересчитывается на сервере — с клиента список не принимается).

- **Парсим регулярками, без cheerio/jsdom.** Блок простой, зависимость ради него не нужна.
  Границы `ul.contact__list` ищутся со счётчиком вложенности (внутри карточек свои `<ul>`).
- **Телефон — последний из карточки** (первый у всех общий, офисный). Берём цифры из
  `href="tel:"` и форматируем сами (`formatQmediaPhone` → `+375 (29) 335-23-23`), потому что
  на сайте формат плавает: `+375 29` / `+375 (29)`, `635-25-13` / `6352323`. Мессенджеры не
  трогаем: их ссылки — `viber://`/`whatsapp://`/`telegram.me`, под `tel:` они не попадают.
- **🛑 Сайт тасует карточки при каждой загрузке** (два подряд запроса дают разный порядок) —
  поэтому порядок с сайта не переносится, `mergeManagersFromSite` сортирует результат по
  имени. Иначе справочник перемешивался бы на каждой синхронизации.
- **Должность (`role`) видимой разметкой не выводится** — она в атрибуте `data-profile`
  у `.contact-manager` (добавлен на сайт специально под эту синхронизацию, 06.08.2026).
  Карточка без атрибута разбор не ломает: `role` тогда остаётся прежним.
- **Фото качаются целиком** (`fetchQmediaPhotos`, по 4 параллельно), а не сохраняются
  ссылкой: картинка нужна и когда qmedia.by лежит, и после того, как там переложат файлы.
  Одна неудачная картинка (404, не картинка, больше 1 МБ) — это `console.warn` и «фото
  осталось прежним», а не падение всей синхронизации.
- **Сравниваются отпечатки файлов, а не адреса.** Имя файла на сайте содержит хеш
  (`andrejmini-180x-1b9.png`), но полагаться на это нельзя: картинку могут заменить, не
  меняя адрес. Поэтому фото качаются **и в предпросмотре тоже** (~530 КБ, ~2 с на весь
  справочник) — иначе менеджер, у которого поменялось только фото, не попал бы в план, и
  кнопки «Применить» пользователь бы не увидел. Такая правка идёт в `updated` плюс
  отдельной строкой «Скачать фото» (`photosChanged`).
- Сопоставление — по имени (`normalizeName`: регистр, лишние пробелы, ё→е), при совпадении
  сохраняется `id` — ссылки в старых КП не ломаются. Всё остальное (имя, должность,
  телефон, email, фото) перезаписывается сайтом: ручные правки этих полей не переживают синк.
- Пустое значение с сайта не затирает заполненное у нас (скорее всего это дырка в данных
  сайта, а не «контакт удалили»); то же с фото — не скачалось, остаётся прежнее. Если блок
  не найден — ошибка «изменилась вёрстка», справочник не трогается.
- **Предпросмотр — модалка, и это не украшательство.** Кнопка «Забрать с qmedia.by» стоит
  под списком из десятка карточек, а панель плана рендерилась в начале секции — при клике
  она уезжала за верхний край экрана (замерено: `top: -544px`), и пользователь видел, что
  «ничего не произошло», а данные не обновились. Туда же уезжали бы сообщения об успехе и
  ошибке, поэтому ошибки синхронизации живут в отдельном состоянии `syncError` и
  показываются внутри модалки, а после применения страница скроллится наверх, к итогу.
- Тесты — `__tests__/qmedia-managers.test.ts` (фикстура повторяет реальную разметку).

Как это доходит до расчёта:

- **Правка настроек не меняет уже сохранённые КП.** При сохранении КП в него кладётся снимок
  `Proposal.calcConfig`; PDF/Excel считают именно по нему (`mergeCalcConfig(proposal.calcConfig)`),
  у старых КП поля нет → `DEFAULT_CALC_CONFIG`. Пересчитать старое КП по новым настройкам =
  импортировать его JSON заново (импорт всегда берёт текущие настройки).
- **Тексты работ фиксируются копированием**, а не снимком настроек: `Wizard.initDirections`
  переносит строки каталога в `DirectionSelection.works`, дальше КП живёт со своей копией
  (PDF и Excel читают только `proposal.directions[].works` и в каталог не заглядывают).
  Поэтому отдельного `Proposal.worksConfig` нет и не нужно, а импорт JSON сохраняет тексты
  из файла — пересчёт по текущим настройкам касается только цен.
- Клиентские компоненты (`CostPanel`, `StepReview`) настройки **не запрашивают** — получают
  `config` пропсом от серверной страницы; сервер при сохранении применяет свою копию.
  Так же и каталог работ: `Wizard` берёт его пропсом (`works`) и один раз фиксирует в
  состоянии (`useState(() => buildWorksCatalog(works))`), `StepDirections` получает готовый
  `catalog` — правка настроек в соседней вкладке не перетасует уже размеченные работы.
- Формы держат числа **строками** (`CalcDraft` в `SettingsCalc.tsx`), иначе не набрать «1,»;
  в числа они превращаются при сохранении, там же собираются ошибки. Валидация на сервере —
  `calcConfigSchema` (zod, `lib/validation.ts`), затем `mergeCalcConfig` для канонизации.
- Через интерфейс **не** меняются: валюта (BYN), варианты срока (3/6), списки опций, названия
  и порядок направлений, правила округления — они завязаны на типы и вёрстку.

Менеджер КП (`Proposal.manager`) — отдельный шаг визарда (`StepManager`): выбор из справочника
или ручной ввод; поля можно поправить «только для этого КП» (отвязывается от справочника).
Пустое имя = «не указывать», тогда PDF/Excel подставляют `COMPANY.manager` (как было раньше).

## Доменная логика (расчёт)

- База `750`, час `75` BYN — это **значения по умолчанию**; фактические берутся из `CalcConfig`
  (третий аргумент `calculate`/`calculateSchedule`). Цена направления/мес =
  `base × коэф.направления × Π(применимые коэф.)`, округление до целого; часы = `round(цена / час)`.
- Наборы коэффициентов **различаются** по направлениям (см. `DIRECTION_COEFFICIENTS`):
  Коммерческое/GEO — все; Информационное/SERM — без страниц/ошибок/конкуренции;
  Техподдержка — только страницы/ошибки/опыт.
- Итог/мес = сумма включённых.
- **Помесячный состав** (главное отличие от Excel-исходника). Направление активно не на весь срок,
  а в произвольный набор месяцев: `DirectionSelection.activeMonths: number[]` (1-based; `[]` = не
  входит). «Включено» = `activeMonths.length > 0`. Срок остаётся 3/6 мес.
  - `calculate(input, directions)` (lib/calc.ts) — **неизменное ядро одного месяца** (на нём держится
    золотой тест). `calculateSchedule(input, directions)` — надстройка: для каждого месяца строит срез
    активных направлений и зовёт `calculate`, затем суммирует. Возвращает `ScheduleResult`
    (`months: MonthBreakdown[]`, `perDirection: DirectionScheduleCalc[]` с `activeMonths`/`monthsLabel`/
    `pricePerMonth`/`fullPricePerMonth`/`hoursPerMonth`/`totalPrice`, грандтоталы). Итог за срок =
    **сумма помесячных**, а не месяц × срок. `*PerMonth` — значения по активным месяцам (могут
    различаться: скидка действует только в месяцы с Коммерческим), из них PDF берёт цифры «в месяц».
  - `Proposal.calcSnapshot` теперь `ScheduleResult`. Все потребители (CostPanel, StepReview, PDF, Excel,
    storage) считают через `calculateSchedule`.
  - **Обратная совместимость**: старые КП в БД хранят `included: boolean` без `activeMonths`.
    `normalizeActiveMonths` (lib/calc.ts) приводит к `activeMonths` (`included:true` → все месяцы), а
    `validation.ts` принимает оба поля. Поэтому рендер старых JSON безопасен.
  - UI ввода — матрица «направления × месяцы» в `StepDirections`; смена срока ремапит `activeMonths`
    (`Wizard.remapMonths`). Подпись месяцев — `formatMonthRanges` (lib/format.ts).
- **Пакетная скидка** (`config.bundle`, дефолт — `COMMERCIAL_BUNDLE` в `seo-config.ts`): если
  включено **Коммерческое SEO**, то включённые **GEO и SERM** считаются со скидкой **30%** (`monthlyPrice` =
  `round(fullMonthlyPrice × 0.7)`; часы — от цены со скидкой). Применяется **помесячно**: в месяце,
  где активно Коммерческое, активные GEO/SERM этого месяца идут со скидкой, иначе — по полной (это
  выходит само за счёт `calculateSchedule`, вызывающего `calculate` помесячно). В `DirectionCalc` есть
  `fullMonthlyPrice`/`discountRate`, в `ScheduleResult` — `totalFullPrice`/`totalDiscount`.
  Скидку показываем всюду: CostPanel, StepReview, PDF (смета + слайд работ направления; в PDF —
  помесячно, см. «Структура PDF»), Excel (колонки «Полная цена за срок» и «Скидка за срок»).
  Нет в исходном Excel — это бизнес-правило.
- **Золотой тест** (значения из кэша Excel — это **полные** цены до скидок): Вся РБ, b2b, до 1000,
  Единичные, Сайт продвигался, Базово, Средняя → `1525/1155/1307/825/540`, сумма полных
  **5352 BYN**. С пакетной скидкой (Коммерческое включено) GEO→`915`, SERM→`578`, итог/мес =
  **4713 BYN / 62 ч**, скидка **639 BYN**. Считается по дефолтному конфигу (тест зовёт `calculate`
  без третьего аргумента) — так и должно остаться. Любая правка расчёта обязана оставлять
  `npm test` зелёным. Тесты `calculateSchedule`/`formatMonthRanges` — там же, а
  `__tests__/calc-config.test.ts` проверяет `mergeCalcConfig` и расчёт по изменённым настройкам.

## Принятые решения и допущения

- Валюта **BYN**. Срок 3/6 мес. Итог за срок = **сумма помесячных** итогов (см. `calculateSchedule`),
  т.к. набор направлений может различаться по месяцам (раньше было месяц × срок).
- «Ссылочное продвижение» и «Конкуренция» — поля формы (есть в Excel, не было в ТЗ).
- «Что продвигаем» **не влияет** на цену (нет коэффициента) — только текст в КП.
- «до 500» страниц в Excel **отсутствует** → коэффициент `1.1` (допущение, правится в настройках).
- Авторизации нет (MVP, внутренний инструмент) — настройки открыты всем, кто дошёл до `/settings`.
- Сохранённое КП — **неизменяемый снимок**: и расчёт (`calcSnapshot`), и настройки
  (`calcConfig`), и менеджер (`manager`), и тексты работ (`directions[].works`). Пересчёт по
  новым настройкам — только через импорт JSON (и он меняет цены, а не формулировки работ).

## Грабли и уроки (важно!)

- **`@react-pdf/renderer` + Next: динамические узлы (`render`-проп) не выводятся.** Номера
  страниц через `render={({pageNumber})=>...}` не рендерятся (молча, ничего не видно).
  Поэтому подвал статический. Подробности и путь к фиксу — в памяти проекта
  `react-pdf-dynamic-nodes-next.md`. Не чинить позиционированием — дело не в нём.
- **Шрифт PDF.** Используется PT Sans (`public/fonts/QmediaSans-*.ttf`, OFL, с кириллицей),
  регистрируется в `ProposalPdf.tsx`. У него **нет** глифа `→` — заменять на тире через
  хелпер `clean()`. Нет и `✓`/`✗`: галочки/крестики в списках рисуются `<Svg><Path>`
  (`CheckIcon`/`CrossIcon`), маркер месяца в матрице — `View`-кружком. Курсив
  (`fontStyle: "italic"`) **не синтезируется** — без отдельного italic-файла будет ошибка
  «Could not resolve font». Системный Arial есть, но проприетарный — не коммитить.
- **`marginTop: "auto"` в react-pdf ненадёжен.** Чтобы прижать блок к низу листа, ставить
  распорку `<View style={{ flexGrow: 1 }} />` перед ним (см. `s.spacer` и `Slide`).
- **Текст в цветной плашке НЕ центрируется сам.** При `lineHeight: 1` react-pdf сажает
  базовую линию почти на низ строчного бокса, поэтому глиф оказывается ниже центра плашки
  на `0.164 × кегль` (коэффициент `GLYPH_SINK_RATIO`, выверен замером на кеглях 8/10.5/14 —
  смещение строго пропорционально кеглю). Не «поправлять на глаз», а брать хелперы
  `ProposalPdf.tsx`: `opticalCenter(fs)` — для flex-центрирования (кружки нумерации),
  `platePadding(fs, pad)` — для плашки на паддингах (жёлтые блоки сумм, бейджи срока;
  высоту не меняет), `centerTextTop(h, fs)` — для абсолютной строки (заголовок колонтитула).
  **Хелперы работают только вместе с `lineHeight: 1`** — при унаследованном 1.4 глиф, наоборот,
  встаёт чуть ВЫШЕ центра, и поправка удваивает ошибку (наступали: бейдж уехал на −3pt).
- **В строке таблицы кегль всех ячеек должен совпадать.** `alignItems: "center"` и
  `"baseline"` на такой строке react-pdf **игнорирует** (проверено рендером — вывод
  побайтово тот же), а разный кегль даёт разную высоту строчного бокса и текст встаёт на
  разной высоте. Поэтому `mtxHeadCellCenter` = `tHeadCell` = 9, `mtxTotalCellCenter` =
  `tTotalCell` = 10. Меняешь кегль в одной ячейке — меняй во всех ячейках строки.
- **Как проверять выравнивание.** На глаз не видно: речь о долях пункта. Рендерить и мерить
  пиксели — `pdftoppm -r 600` в PPM (формат P6 парсится в 10 строк), заливкой найти цветную
  плашку и сравнить её центр с bbox текста. Важно: **ink-bbox — не то же, что оптический
  центр.** Выносные элементы (запятая в «9 150,00», «р» в «Направление», «/») тянут bbox
  вниз и дают ложное «смещено» на 1–2pt; скруглённые углы плашки подмешивают фон. Сверять
  надо **верх литер** — если он совпал, базовые линии совпали.
- **react-pdf: крупный `fontSize` + унаследованный `lineHeight` 1.4 → текст налезает на
  соседний.** Для больших чисел/заголовков ставить `lineHeight: 1` + `marginBottom`.
- **Абсолютный элемент только с `right` схлопывает ширину** (текст не виден). Задавать
  `left` + `right` + `textAlign`.
- **🛑 react-pdf ВЕШАЕТ раскладку (синхронный бесконечный цикл), если абсолютная `<Image>`
  с отрицательным смещением / выходящая за край лежит прямо в `<Page>`.** Симптом: рендер
  висит вечно, vitest не показывает даже таймаута теста (event loop заблокирован). Лечение:
  оборачивать такие watermark-картинки в контейнер с `overflow:"hidden"` (см. обложку и
  колонтитул `HeaderBand` в `ProposalPdf.tsx`). Диагностика — бисекция через esbuild-бандл
  + `execFileSync(..., {timeout})` (vitest тут бесполезен — воркер виснет молча).
- **`Buffer` → `Response`.** TS ругается на `BodyInit`; оборачивать в `new Uint8Array(buffer)`.
- **Бутстрап.** Папка не пустая (`sources/`) — `create-next-app` откажется; проект собран
  конфигами вручную.
- **Хранилище — Postgres, не файлы.** Раньше КП лежали в `data/proposals/*.json`; на serverless
  (Vercel) ФС эфемерна и данные терялись бы. Теперь — таблица `proposals` в Postgres
  (Neon/Supabase), `data jsonb`. На Vercel в `DATABASE_URL` класть **pooled/pooler** строку
  подключения (иначе можно упереться в лимит коннектов). Колонка `id` — `text` (id всегда из
  `crypto.randomUUID`), чтобы не ловить ошибки каста `uuid` на «мусорных» id. Настройки — там же,
  в `app_settings` (ключ → jsonb); схему и разовые правки данных накатывает `lib/migrations.ts`
  через `ensureSchema()` (см. «Миграции»).
- **JSON из БД нельзя типизировать «на веру».** Настройки и снимок `Proposal.calcConfig` —
  произвольный jsonb (может быть от старой версии или поправленным руками), поэтому читаются
  только через `mergeCalcConfig` / `normalizeManagers`: недостающее берётся из дефолтов,
  мусор отбрасывается. `Proposal.calcConfig` намеренно объявлен `unknown` — чтобы это нельзя
  было обойти и чтобы `types.ts` не зависел от `calc-config.ts`.
- Тяжёлые пакеты (`@react-pdf/renderer`, `exceljs`) вынесены во внешние через
  `serverComponentsExternalPackages` в `next.config.mjs`.

## Конвенции

- **Бренд green-forward.** Основной цвет — зелёный `#53BD35`, акцент — жёлтый `#FFDE00`
  (сверены с CSS qmedia.by). Чёрный почти не используется (только тёмный текст). Палитра
  в `BRAND` (`lib/company.ts`) и `tailwind.config.ts` зеркальны. Логотипы — `public/brand/logo-*.svg`
  (в вебе SVG; в PDF — белые PNG, т.к. react-pdf не грузит SVG через `<Image>`).
- **Жёлтый — только подложка или мелкая графика, никогда не текст:** `#FFDE00` на белом
  нечитаем. В PDF он живёт в фиксированных местах: отбивка колонтитула (`bandRule`, на каждом
  листе), черта под заголовком обложки, кружки нумерации (`numCircle`, тёмный текст на жёлтом),
  черта у лейбла итоговой полосы слайда (`stripBar`), суммы (`costHighlight` в смете,
  `dirCostSum` на слайде работ), бейдж срока направления (`dirBadgeOn`), карточка «30+»
  и подчёркивания цифр «о компании» (`statBar`). Зелёная черта = заголовок раздела
  (`subBar`), жёлтая = вывод/итог — эту пару не смешивать.
- **Карточки-плашки — без левого бордера, фон `BRAND.light` (#F6F7F9).** Скругление плюс
  цветная черта слева выглядели грязно, поэтому у `workCard`/`roleCard` бордера нет.
  Левая черта осталась только там, где нет скругления: `note` (зелёная, «Почему это важно»)
  и `dirCostCell` (разделитель колонок баннера).
- **Общение с пользователем — только на русском** (техн. идентификаторы как есть).
- Литералы значений в типах/конфиге совпадают со значениями Excel — чтобы выгрузка и расчёт
  были зеркальны исходнику. Не переименовывать без необходимости.
