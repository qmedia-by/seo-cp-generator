# CLAUDE.md

Заметки для будущих сессий по проекту **«Генератор КП по SEO — Qmedia»**.
Подробности для людей — в [README.md](README.md). Здесь — карта кода, доменная логика и
неочевидные грабли, на которые уже наступили.

## Что это

Внутренний инструмент Qmedia: по параметрам проекта считает стоимость SEO по 5 направлениям,
генерирует **PDF** (КП для клиента) и **Excel** (план + расчёт), сохраняет каждую генерацию
JSON-файлом, умеет импортировать JSON и пересчитывать. Ставки/коэффициенты расчёта, списки
работ по направлениям и справочник менеджеров правятся через интерфейс (`/settings`) —
см. «Настройки».

Стек: **Next.js 14 (App Router) + TypeScript + Tailwind**, `@react-pdf/renderer` (PDF),
`exceljs` (Excel), `zod` (валидация), `vitest` (тесты), **Postgres** (Neon/Supabase) через `pg`.

## Команды

```bash
npm run dev     # dev (порт 3000, при занятости — 3001 и т.д.); нужен DATABASE_URL в .env.local
npm run build   # прод-сборка (заодно полная проверка типов)
npm test        # юнит-тесты расчёта (БД не требуется — calc чистый)
npx tsc --noEmit
```

Хранилищу нужен Postgres: задать `DATABASE_URL` в `.env.local` (шаблон — `.env.example`).
Локально проще всего через `Makefile` (поднимает Postgres в Docker + dev-сервер):

```bash
make init      # зависимости + .env.local + контейнер Postgres (seocp-pg)
make dev       # dev-сервер в foreground; make start — фоном; make stop/restart/status/logs
```

`make start` запускает `npm run dev` фоном с `nohup`, PID — в `.dev-server.pid` (gitignored),
логи — `.dev-server.log`; `stop-dev` гасит дерево процессов по PID (через рекурсивный `pgrep`),
`db-stop` делает `docker stop` (данные в томе `seocp-pgdata` сохраняются). Без Docker — обычный
`docker run ... postgres:16-alpine` и ручной `DATABASE_URL`.

## Карта кода

- `lib/seo-config.ts` — ставки и коэффициенты **по умолчанию** (выверено по
  `sources/Расчет SEO.xlsx`) плюс списки опций форм, названия и порядок направлений.
  Числа отсюда — только дефолты: рабочие значения живут в БД (см. `lib/calc-config.ts`).
- `lib/calc-config.ts` — `CalcConfig` (всё, что настраивается через интерфейс),
  `DEFAULT_CALC_CONFIG` (собран из `seo-config.ts`), `mergeCalcConfig` (толерантное чтение
  «сырого» JSON из БД: битое/отсутствующее заменяется дефолтом) и метаданные для формы
  настроек (`COEF_GROUPS` — подписи и пояснения).
- `lib/calc.ts` — чистая функция `calculate(input, directions, config?)`. Логика 1:1 с Excel;
  без третьего аргумента считает по `DEFAULT_CALC_CONFIG` (на этом держится золотой тест).
- `lib/works-catalog.ts` — 5 направлений: ключ, название, цель и работы **по умолчанию**
  (из `sources/Разбивка SEO по блокам работ.md`). Рабочие списки работ живут в БД
  (см. `lib/works-config.ts`); название и цель через интерфейс не меняются.

  `mergeWorksConfig` (толерантное чтение jsonb: битое/отсутствующее направление берёт
  дефолт, тексты чистятся и дедуплицируются) и `buildWorksCatalog` — каталог для визарда

- `lib/storage.ts` — хранилище КП в Postgres (таблица `proposals(id, created_at, data jsonb)`).

  У читающих функций две версии:

## Структура PDF

**Формат — 16:9, 720×405 pt.** Это ровно канва презентации дизайнера
(`sources/cp-seo-deck.pdf` — экспорт исходных макетов, 36 слайдов; в `.pptx`
канва 9144000×5143500 EMU), поэтому координаты и кегли из макетов переносятся
в код 1:1, без пересчёта. Раньше был A4 landscape — от него отказались вместе
с переездом на макеты (КП уходит клиенту почтой и смотрится с экрана).

Нумерация «макет N» в комментариях кода — это номер слайда в `cp-seo-deck.pdf`.

Продающая логика: сначала подход, потом цена и направления, потом команда и снятие
возражений. Порядок закреплён (менялся по согласованию — не переставлять «заодно»):

```
 1      Обложка (макеты 1–8): имя, должность и фото менеджера, который КП подготовил
 2–6    Подход: макеты 9–13 (что вы получите · рынок · «по старинке» · экосистема · путь клиента)
 7      Смета — своего макета нет, переоформлена под общую стилистику
 8…N    По два листа на направление (итерация по `proposal.directions`, порядок сметы):
          • описание — макеты 14–18 по ключу направления (`PITCH_DIRECTIONS`),
            плюс плашка `DirectionBadge` со сроком из расчёта;
          • состав работ — баннер «стоимость в месяц · период · объём» + карточки работ
 N+1    Команда: макет 19 (зелёный разделитель) + 20 (профильная команда)
 N+3    Project-менеджер — макеты 21–25, упрощённые (см. ниже)
 N+4    Аналитика и отчётность — макет 26
 N+5    Гарантии: макеты 27 (разделитель), 28, 29, 30, 31
 N+10   О компании: макеты 32 (разделитель), 33, 34, 35, 36
```

Итого **30 листов** при полном каталоге. От расчёта зависят только смета, слайды
состава работ и бейджи сроков на описаниях направлений.

- Слайд *описания* показывается **всегда**, даже для выключенного направления (бейдж
  «не входит») — клиент видит весь спектр услуг.
- Слайд *состава работ* — **только при `activeMonths.length > 0`**: расписывать работы,
  которых нет в предложении, незачем.
- Состав работ режет пункт каталога по первому ` — ` (`splitWork`): жирный заголовок,
  ниже серое описание. У произвольных работ тире может не быть — тогда весь текст идёт
  заголовком. Список **длиннее 6 работ раскладывается в три колонки**: полный каталог
  (11 работ) в две колонки — шесть рядов карточек, и в 405 pt они не помещаются.
  Отступ между рядами карточек зависит от числа рядов (`rowGap` в `direction.tsx`):
  коротким спискам достаётся свободная нижняя треть листа. Растёт **только отступ**,
  не кегль: высота карточки зависит от длины работы, а её правят в настройках.
- **Слайд Project-менеджера упрощён относительно макета** (правка заказчика от
  19.08.2026): убраны ссылка «видеовизитка» и список личных достижений — вести его на
  каждого менеджера накладно. В карточке — только то, что и так есть в справочнике:
  фото, имя, должность, «Смотреть резюме» и кликабельные контакты. Вывод слайда —
  жёлтая плашка во всю ширину листа, без иконки-лайка (правка от 20.08.2026).
- **На слайде «Профильная команда» нет скрепки** — плашка с выводом идёт во всю ширину
  колонки (правка от 20.08.2026).
- **Аватарка Project-менеджера на слайде «Профильная команда»** берётся из КП: это тот
  же человек, что и на следующем листе, статичного фото для него быть не может.
- **Крупная цифра в PDF — всегда платёж за месяц, не сумма за срок** (фидбэк отдела продаж
  от 05.08.2026: «17 тыс. за 3 месяца — дорого и страшно, дробить»). Жёлтые плашки сметы
  и слайда работ показывают месяц; сумма за срок остаётся, но обычной строкой: в карточке
  сметы («Итого за N»), в колонке «За срок» серым и в подписи ячейки «Период работ».
  Помесячные величины берутся из `pricePerMonth`/`fullPricePerMonth`/`hoursPerMonth`
  (`DirectionScheduleCalc`) и `calc.months`, форматируются
  `formatMonthlyMoney/Amount/Hours` (lib/format.ts): месяцы одинаковы → одно число, разные
  → «от N» (детали клиент видит в матрице «Состав по месяцам»). На жёлтых плашках
  приставку «от» печатает `SumText` (primitives) — **мельче самой цифры**
  (`FROM_PREFIX_RATIO`): это уточнение, а не часть суммы. Разбирает строку
  `splitFromPrefix` (lib/format.ts), приставка идёт отдельным inline-`<Text>` —
  соседние runs внутри одного `<Text>` react-pdf сажает на общую базовую линию.
- Строки «Без скидки в месяц» / «Экономия» в смете показываются помесячно **только когда
  набор направлений одинаков во все месяцы** (`sameEveryMonth`): иначе минимумы по строкам
  пришли бы из разных месяцев и не сходились бы между собой — тогда экономия даётся за срок.
- **Ссылки живые.** Телефон и почта в подвале каждого листа, соцсети и мессенджеры,
  разделы сайта, «Ещё больше инструментов», кейсы, резюме менеджера — всё `<Link>`.
  Адреса собраны в `LINKS`/`SOCIALS` (lib/company.ts) и в `PITCH_CASES`.
- **Вертикаль 405 pt тесная — любая правка отступов ломает пагинацию.** Самые плотные
  листы: смета (параметры + карточка стоимости + матрица на 5 направлений), состав работ
  на 11 пунктов, «Аналитика» (три колонки метрик + формат отчётности), «Платный
  инструментарий» (14 карточек сервисов) и описание GEO/AEO (третья колонка с
  расшифровкой терминов — там кегли специально мельче, `dense` в `direction.tsx`).
  Меняешь размеры/отступы — **перепроверяй числом
  листов в рендере**: лишняя страница = что-то не влезло (`Slide` намеренно оставлен
  переносимым, чтобы это было видно). Проверять надо не один набор данных: 3 и 6
  месяцев, полный каталог работ и короткий, все направления и одно —
  раскладка у них разная.

### Смена шрифта и пагинация

**🛑 Смена шрифта в колоде — это не одна строка в `theme.ts`.** Ширина строки меняется,
вместе с ней меняется число переносов, и листы начинают рассыпаться. При переезде
PT Sans → Verdana (20.08.2026) разъехалось **15 листов из 31**: описания и составы работ
всех направлений, «SEO на заявки», «по старинке», «путь клиента», обе командные,
«Аналитика» и «Платный инструментарий». Лечится не шрифтом, а кеглями и отступами —
их пришлось подрезать назад примерно до значений, которые были до правки
«разрежённая вёрстка» от 20.08.2026 (та правка раздавала свободное место, оставшееся
от более узкого PT Sans).

Порядок работы, если шрифт меняют снова:

1. **Замерить ширину** новым шрифтом против старого (`fontkit`, `layout(...).advanceWidth`)
   на реальных строках колоды — отдельно regular и bold. У Verdana против PT Sans вышло
   ×1.20 и ×1.33.
2. **Пересчитать оптику**: `ASCENT_RATIO` и `CAP_RATIO` в `theme.ts` — из `hhea.ascent`
   и `OS/2.capHeight` шрифта, делённых на `unitsPerEm`. Проверить рендером в 300 dpi на
   крупном кегле (120–200 pt, чтобы квантование не мешало).
3. **Считать листы, а не смотреть глазами.** Рендерить набор КП и сверять число страниц
   с эталоном: полный каталог × 3 мес, × 6 мес, один направление с коротким списком,
   разный набор направлений по месяцам. Норма при полном каталоге — **31 лист**; лишний
   лист = что-то не влезло (`Slide` намеренно оставлен переносимым, чтобы это было видно).
4. **Проверить, что не осталось пустоты.** Низ контента (`ink bottom`) должен лежать
   в районе 300–344 pt: 344 — предел (`PAGE_H − PAD_BOTTOM`), сильно меньше 300 — лист
   выглядит пустым. Слишком агрессивная подрезка чинит пагинацию и ломает вёрстку.
5. **Проверить поля по горизонтали**: ink не должен вылезать за 26…694 pt.
6. **Проверить `pdffonts`**: должны быть ровно четыре начертания нового шрифта и
   **никакой Helvetica** (её подмешивает перевод строки внутри одного `<Text>`).

Общие примитивы — в `lib/pdf/primitives.tsx`: `Slide` (белый лист: водяной знак, контент,
зелёный подвал), `GreenSlide` (зелёный лист-разделитель), `SlideHead` (чёрный заголовок +
жёлтая подпись), `HlLine` (строка с жёлтой плашкой на куске фразы), `Kicker`, `Bullets`,
`NoteBox`, `Avatar`, `PillLink`, `Cursor`, `Overlay` и `rich()`/`Rich` — разбор разметки
`**жирный**` / `==жёлтый==`.

### Жёлтое выделение куска фразы

`==…==` внутри строки рисуется **плашкой** — `View` с фоном (`HlLine`), а не
`backgroundColor` на inline-`<Text>`.

**🛑 У inline-варианта высоту подложки задаёт строчная коробка шрифта.** Глиф сидит в её
нижней части, поэтому жёлтое выпирает над прописными и почти касается базовой линии
снизу; подбором `lineHeight` симметрии не добиться — коробка растёт только вниз
(замерено). Заказчик это и увидел: «вертикально выравнять жёлтую подложку, чтобы не
завязываться на особенности шрифта».

Геометрия задана в `theme.ts` (`plateText`, `PLATE_GAP_RATIO`) и опирается на два
источника:

- **метрики шрифта**: react-pdf при `lineHeight: 1` сажает базовую линию ровно на
  `hhea.ascent × кегль` ниже верха строчной коробки, а `lineHeight` растягивает коробку
  только ВНИЗ — поэтому верх прописных от него **не зависит**. Отсюда
  `CAP_TOP_RATIO = ASCENT_RATIO − CAP_RATIO` (для Verdana `1.005 − 0.727 = 0.278`;
  у прежнего PT Sans было `1.018 − 0.700 = 0.318`). Проверено пиксельным замером
  рендера в 300 dpi на кеглях 120 и 200 (там квантование пренебрежимо): замер совпал
  с расчётом до 0.001;
- **макет** (слайд 12, «5 типов SEO»): плашка 38.4 pt при прописных 24.24 pt, сверху
  6.96 pt, снизу 7.20 pt — симметрично, ≈`0.21 × кегль`. Это `PLATE_GAP_RATIO`.

Отсюда `plateText`: отрицательный `marginTop` подтягивает строку вверх (укорачивая
плашку сверху), `lineHeight` добирает столько же воздуха снизу. Воздух над прописными
и под базовой линией выходит **точно одинаковым** — это следует из формул, а не из
подбора: обе величины равны `PLATE_GAP_RATIO × кегль`.

`HlLine` собирает строку флекс-рядом: плашки и обычный текст имеют одинаковую
внутреннюю геометрию, поэтому базовые линии совпадают, а `alignItems: "flex-end"`
держит плашку на последней строке, если обычный кусок перенёсся. Пробел на стыке с
плашкой — это `marginLeft`, а не пробел в тексте: react-pdf срезает пробел в конце
`<Text>`, и слово прилипало бы к плашке.

**Где применяется:** строки заголовков (`SlideHead`) и шапка правой колонки на слайдах
направлений (`resultTitle`). Внутри абзаца, который может перенестись, плашкой хайлайт
не сделать — там у `rich()` остаётся inline-вариант (сейчас таких текстов в колоде нет).

**🛑 Высота строки заголовка теперь `1.14 × кегль`** (была `1.05`), а воздух между
строками даёт `marginBottom` (`0.19 × кегль` в `SlideHead`). Меняешь кегли заголовков —
перепроверяй пагинацию: смета и «Аналитика» держались на паре пунктов запаса.

### Скругления

В макетах углы острые — небольшое скругление добавлено по правке заказчика. Шкала —
`R` в `theme.ts`: `sm: 3` (бейджи, плашки-хайлайты), `md: 6` (карточки, боксы, плашки
сумм), `lg: 10` (крупная карточка Project-менеджера), `pill: 999` (кнопки-таблетки —
у дизайнера они уже такие: `roundRect adj=50000`).

**Фоторамки — исключение: у них углы прямые** (`Framed` по умолчанию `radius: 0`).
Правка заказчика от 20.08.2026: награды, сканы отзывов, обложки кейсов и карта должны
быть «как в макете». Аватар — тоже не про `R`: это два вложенных круга (см. ниже).

### Типографика (`lib/pdf/typography.ts`)

Автоперенос react-pdf регулярно оставлял висячие предлоги («…конкурентов и / ссылок»)
и одинокие слова на последней строке («…специалиста в / штате»). Лечится не вёрсткой,
а неразрывными пробелами: `typography()` расставляет их один раз для всей колоды —
функция вызывается из `clean()`, а через `clean()` (напрямую или через `rich()`)
проходит каждая строка.

Правила: NBSP после предлогов/союзов/частиц (закрытый список, «все» не предлог),
после числа («46 инструментов», «30 000 $»), перед тире и «=», и между двумя
последними словами абзаца, если они короткие (пороги `WIDOW_*`).

- **🛑 NBSP склеивает слова в один токен для переносчика** — группа шире колонки
  вылезет за край. Пороги выверены по самой узкой колонке колоды (описания сервисов
  на слайде инструментария, ~35 знаков), поэтому правила намеренно консервативные.
- **🛑 NBSP на границе алфавитов даёт лишний дефис.** «в<NBSP>AI-ответах» становится
  одним словом из двух runs `scriptItemizer`, между ними встаёт penalty-узел и при
  переносе печатается «в -» / «AI-ответах» — те же грабли, что у колбэка переносов
  в `theme.ts`, но колбэк тут не помогает (penalty ставит сам textkit). Поэтому
  кириллица с латиницей не склеивается (`crossesScripts`).
- Знаки-связки сверяются с **сырым** токеном: `core()` вычищает всё, кроме букв и
  цифр, и от «—» или «=» ничего бы не осталось.
- Где автоматики мало (крупные заголовки, подписи зелёных разделителей), строки
  разбиты руками — массивом строк в `lib/pitch.ts`. Так же, как в макете.

### Водяные знаки — вектор

Знак «Q» на листах рисуется примитивом `QMark` (`<Svg><Path>` по `Q_MARK` из
`assets.ts`), а не картинкой: растр `bg-q-grey.png` был 511 px на 559 pt отрисовки
(≈66 dpi) и заметно мылил. Прозрачности вынесены в `theme.ts`
(`GREEN_WATERMARK_OPACITY`, `COVER_WATERMARK_OPACITY`) — заказчик просил сделать
знаки заметнее, чем было (0.12 / 0.15).

### Аватар — два вложенных круга

**🛑 Жёлтое кольцо нельзя делать бордером на том же блоке, что и картинка.**
`overflow: hidden` режет содержимое по окружности **бордер-бокса**, а квадратная
картинка внутри достаёт до неё по диагоналям — от кольца остаются четыре серпика по
сторонам света («рамка не по кругу»). Поэтому `Avatar` — внешний жёлтый круг и
вложенный круг поменьше на толщину кольца, уже со своим `overflow: hidden`.

## Деплой (Docker, своё облако)

Хостинг переезжает с Vercel/Supabase на собственный сервер с Docker. Схема повторяет
CI соседнего проекта qmedia (образы в GHCR, compose на сервере, единый серверный `.env`):

- `docker/Dockerfile` — multi-stage образ приложения: `npm ci` → `next build`
  (**`output: "standalone"`** в `next.config.mjs`) → тонкий runtime `node:22-alpine`.
  Контекст сборки — корень репо (лишнее режет `.dockerignore`). БД на сборке не нужна.
- `docker/docker-compose-server.yml` — серверный стек: `app` (образ из GHCR, порт
  `127.0.0.1:PORT_APP`, наружу — reverse-proxy хоста) + `database` (postgres:16-alpine,
  том `pgdata`). `DATABASE_URL` собирается в compose с `?sslmode=disable` —
  `lib/db.ts` понимает этот флаг и не включает TLS (иначе бы пытался, хост не localhost).
- `.github/workflows/deployment.yml` — деплой на push в `main`/`dev` (environment
  production/development) или вручную: preflight серверного `.env` → юнит-тесты →
  build&push образа в GHCR → дамп БД + запоминание текущего `IMAGE_TAG` → rsync только
  `docker/` → `compose pull` + `up --wait` → health-check → при провале откат на
  предыдущий `IMAGE_TAG`. Код на сервер не синхронизируется — всё в образе.
- Секреты (per-environment): `DEPLOYMENT_HOST/USER/SSH_PRIVATE_KEY/FOLDER`.
  Одноразовый бутстрап сервера: `<DEPLOYMENT_FOLDER>/.env` из `.env.server.example`
  (CI обновляет в нём только `IMAGE_TAG`) + reverse-proxy на `PORT_APP`.
- Отдельного шага миграций в CI нет — их прогоняет `ensureSchema()` лениво при первом
  запросе (см. «Миграции»). Поэтому деплой не зависит от доступности БД в момент выката.
- `keep-supabase-awake.yml` актуален, пока прод-БД на Supabase; после переезда удалить.

### Индексация закрыта

Инструмент внутренний и **авторизации не имеет**, поэтому от поиска закрыт в три слоя —
снимать по отдельности нельзя, каждый закрывает свою дыру:

- `app/robots.ts` → `/robots.txt` с `Disallow: /` — запрещает **обход**, но не индексацию.
- `headers()` в `next.config.mjs` → `X-Robots-Tag: noindex, nofollow, …` на `/:path*` —
  главный слой: запрещает **индексацию** и, в отличие от меты, работает для выгрузок из
  `/api` (PDF/Excel) и статики из `public/`.
- `metadata.robots` в `app/layout.tsx` → `<meta name="robots">` на всех страницах.

**🛑 `Disallow: /` сам по себе от индекса не спасает** — наоборот, он мешает роботу
прочитать `noindex`, и страница может попасть в выдачу по внешней ссылке (без сниппета).
Работает это только в паре с `X-Robots-Tag`, который роботы видят и на закрытых путях,
если всё-таки зашли. Единственная настоящая защита от посторонних — авторизация
(basic auth на reverse-proxy хоста или VPN), robots.txt данные не прячет.

## Миграции

`lib/migrations.ts` — самописный раннер (~50 строк, без зависимостей): массив миграций
`{ id, run(client) }` + журнал `schema_migrations`. Прогоняются лениво из `ensureSchema()`,
никаких CLI и шагов деплоя. Инструмент вроде node-pg-migrate тут дороже: его пришлось бы
тащить в тонкий standalone-образ вместе с файлами миграций и вклинивать шаг между
`compose pull` и `up --wait`.

- **Применённые миграции неизменяемы**: правка/удаление уже выкаченной миграции разведёт
  базы (на проде она отмечена в журнале и не переиграется). Только добавлять следующую.
- **Порядок в массиве = порядок применения**, `id` — `NNNN_смысл`; каждая идёт в своей
  транзакции. Тест в `__tests__/works-config.test.ts` следит за уникальностью и сортировкой
  id.
- **🛑 `CREATE TABLE IF NOT EXISTS` не атомарен.** Два холодных старта одновременно роняли
  друг друга: `duplicate key value violates unique constraint "pg_type_typname_nsp_index"`.
  Поэтому `pg_advisory_lock` берётся **первым**, до создания даже самой `schema_migrations`
  (ловится тестом на двух пулах против чистой БД; прежний `ensureSchema` этой гонке был
  подвержен). SQL всё равно пишем идемпотентным — базы правились руками до появления журнала.
- `0001_init` — `proposals` и `app_settings` (то, что раньше создавал `ensureSchema`);
  `0002_seed_works` — перенос каталога работ из кода в БД (см. «Работы направлений»);
  `0003_manager_photos` — таблица `manager_photos` (см. «Фото менеджеров»).

## Настройки (`/settings`)

Кнопка-шестерёнка в шапке (`app/layout.tsx`). Три вкладки:

- **Данные для расчёта** — весь `CalcConfig`: базовая стоимость, стоимость часа, коэффициенты
  направлений, матрица «какие коэффициенты входят в формулу направления», пакетная скидка
  (триггер + получатели + процент) и все 7 таблиц коэффициентов параметров. Есть сброс
  к дефолтам (`DELETE /api/settings/calc` просто удаляет строку из `app_settings`).
- **Работы направлений** — `WorksConfig`: списки заготовок работ, которые визард предлагает
  отметить. Добавление, правка, удаление и перестановка (↑/↓). См. ниже.
- **Список менеджеров** — фото / Имя Фамилия / специальность / телефон / email /
  ссылка на резюме. Текстовые поля хранятся одним массивом; добавление, правка и удаление
  сразу отправляют список целиком (`PUT`). Фото — отдельной ручкой, см. «Фото менеджеров».
  Пока строки в БД нет, `getManagers()` отдаёт одного менеджера из `COMPANY.manager`.
  Плюс кнопка «Забрать с qmedia.by» — синхронизация с сайтом, см. ниже.
  Этот же справочник питает **оба** шага визарда — «Менеджер» и «Project-менеджер».

Отдельных разделов настроек под тексты слайдов PDF **нет и не заводим** (решение
заказчика): вся статика колоды живёт в коде — `lib/pitch.ts` и `lib/company.ts`.

### Работы направлений

Каталог работ переехал из кода в БД (`app_settings`, ключ `works`), в коде остались только
дефолты (`lib/works-catalog.ts` → `DEFAULT_WORKS_CONFIG`).

- **Правится только список работ.** Ключ, название, цель и порядок направлений остаются в
  коде: на них завязаны вёрстка слайдов, порядок сметы и `PITCH_DIRECTIONS`.
- **Текст работы — её идентификатор** в визарде (по нему стоит галочка и собирается
  `DirectionSelection.works`), поэтому `mergeWorksConfig` схлопывает пробелы и **выбрасывает
  дубли**: две одинаковые строки переключались бы одной галочкой и ломали бы React-ключи.
- **Пустой массив ≠ отсутствие настройки.** Направление без ключа в jsonb получает дефолтный
  список, а явно сохранённый `[]` так и остаётся пустым (в визарде — направление без
  заготовок, только ручные работы). Та же логика, что у справочника менеджеров.
- **Порядок работ значим** — это порядок карточек на слайде «Состав работ» и строк в Excel,
  поэтому в настройках есть ↑/↓, а не только добавление/удаление. Помни про пагинацию PDF:
  лист состава работ подогнан под 11 работ (см. «Структура PDF») — более длинный список
  порвёт лист. Первое ` — ` в тексте делит пункт на заголовок и описание (`splitWork`).
- **Перенос в БД — миграция `0002_seed_works`**, а не посев на каждом старте: списки из кода
  кладутся в `app_settings` один раз и отмечаются в журнале. Дальше **источник истины — БД**:
  правки `works-catalog.ts` на уже мигрированную базу не попадают (списки правят в
  `/settings`).
- **Сброса к дефолтам у работ намеренно нет** (в отличие от вкладки расчёта): кнопка,
  затирающая вручную выверенные формулировки всего каталога, — лишний способ выстрелить
  себе в ногу. `DELETE /api/settings/works` тоже нет.
- Тесты — `__tests__/works-config.test.ts` (merge, каталог, снимок работ в КП, журнал
  миграций).

### Фото менеджеров

Фото — не поле справочника, а отдельная таблица `manager_photos(manager_id, mime, version,
bytes, updated_at)`; в самом справочнике живёт только производное `Manager.photoVersion`
(отпечаток картинки), которое `getManagers()` подмешивает при чтении, а `saveManagers()`
не сохраняет.

- **Почему не base64 в jsonb.** Справочник читается на каждый рендер `/new` и уезжает в
  браузер пропсами (`Wizard` → `StepManager`). 13 аватарок с сайта — это ~530 КБ, в base64
  ~700 КБ: они висели бы в RSC-payload каждой страницы визарда и перезаписывались бы
  целиком при любой правке имени. Так же и `PUT /api/settings/managers` остаётся лёгким.
- **Адрес картинки — со штампом версии**: `/api/settings/managers/{id}/photo?v={photoVersion}`.
  Ответ отдаётся с `immutable` на год, поэтому без штампа браузер показывал бы старое фото
  после замены. Формируется этот адрес в одном месте — `managerPhotoUrl` в
  `components/ManagerAvatar.tsx` (модуль `lib/manager-photos.ts` серверный, `node:crypto`,
  в клиент его не тянем).
- Показывается фото в четырёх местах: карточки в настройках, карточки выбора на шагах
  «Менеджер» и «Project-менеджер» (всё через `ManagerAvatar`) и **в PDF** — на обложке
  и на слайдах команды/Project-менеджера. В Excel фото не попадает.
- **В PDF фото приезжает по ссылке, а не снимком.** В КП сохраняется только
  `ProposalManager.id` (id в справочнике), а байты читаются на рендере —
  `lib/pdf/photos.ts` → `loadProposalPhotos()`, вызывается в route-handler'е PDF **до**
  рендера (документ синхронный). Класть base64 в jsonb КП не стали: два фото ≈ 100 КБ
  на каждое предложение, а `proposals.data` читается целиком в списке КП. Цена решения
  осознана: заменили фото менеджера — в старом КП при повторном скачивании будет новое
  (цифры и тексты при этом остаются снимком). Нет id или фото — рисуется кружок
  с инициалами. react-pdf понимает только PNG и JPEG: WebP из белого списка MIME
  просто не показывается.
- **Файл ужимается в браузере** (`toPhotoDataUrl`): кадр по центру в квадрат 512 px и JPEG
  0.85 — иначе с телефона прилетает несколько мегабайт ради аватарки 48×48. Сервер всё
  равно проверяет MIME и потолок `MAX_PHOTO_BYTES` (1 МБ): клиент — удобство, не защита.
- **Фото сохраняется вторым запросом, после списка.** Порядок принципиален: `saveManagers`
  чистит фото, чьих менеджеров в списке нет, — залей картинку раньше, и её тут же снесло бы
  как ничью. Тот же порядок в синхронизации (`saveManagers` → `saveManagerPhotos`).
- Удаление менеджера фото подчищает автоматически (внешнего ключа нет — справочник в jsonb).

### Синхронизация менеджеров с qmedia.by

Главный источник по менеджерам — блок «Персональные менеджеры» (`ul.contact__list`) на
`https://www.qmedia.by/kontakty.html` (имя, должность, телефон, email, фото и ссылка на
резюме — мессенджеры не берём). `lib/qmedia-managers.ts` его качает и разбирает,
`app/api/settings/managers/sync` отдаёт план (`GET`, ничего не пишет) и применяет его
(`POST`, план пересчитывается на сервере — с клиента список не принимается).

- **Парсим регулярками, без cheerio/jsdom.** Блок простой, зависимость ради него не нужна.
  Границы `ul.contact__list` ищутся со счётчиком вложенности (внутри карточек свои `<ul>`).
- **Телефон — последний из карточки** (первый у всех общий, офисный). Берём цифры из
  `href="tel:"` и форматируем сами (`formatQmediaPhone` → `+375 (29) 335-23-23`), потому что
  на сайте формат плавает: `+375 29` / `+375 (29)`, `635-25-13` / `6352323`. Мессенджеры не
  трогаем: их ссылки — `viber://`/`whatsapp://`/`telegram.me`, под `tel:` они не попадают.
- **🛑 Сайт тасует карточки при каждой загрузке** (два подряд запроса дают разный порядок) —
  поэтому порядок с сайта не переносится, `mergeManagersFromSite` сортирует результат по
  имени. Иначе справочник перемешивался бы на каждой синхронизации.
- **Должность (`role`) видимой разметкой не выводится** — она в атрибуте `data-profile`
  у `.contact-manager` (добавлен на сайт специально под эту синхронизацию, 06.08.2026).
  Карточка без атрибута разбор не ломает: `role` тогда остаётся прежним.
- **Ссылка на резюме — это адрес, в который на сайте обёрнута аватарка**
  (`<a href="andrej_zhuk.html"><img class="contact-manager__avatar">`), разворачивается
  в абсолютный тем же `absoluteUrl`, что и адрес фото. В КП уходит кнопкой «Смотреть
  резюме» на слайде Project-менеджера. В отличие от фото, храним именно адрес: он ведёт
  на сайт, и его актуальность — забота сайта.
- **Фото качаются целиком** (`fetchQmediaPhotos`, по 4 параллельно), а не сохраняются
  ссылкой: картинка нужна и когда qmedia.by лежит, и после того, как там переложат файлы.
  Одна неудачная картинка (404, не картинка, больше 1 МБ) — это `console.warn` и «фото
  осталось прежним», а не падение всей синхронизации.
- **Сравниваются отпечатки файлов, а не адреса.** Имя файла на сайте содержит хеш
  (`andrejmini-180x-1b9.png`), но полагаться на это нельзя: картинку могут заменить, не
  меняя адрес. Поэтому фото качаются **и в предпросмотре тоже** (~530 КБ, ~2 с на весь
  справочник) — иначе менеджер, у которого поменялось только фото, не попал бы в план, и
  кнопки «Применить» пользователь бы не увидел. Такая правка идёт в `updated` плюс
  отдельной строкой «Скачать фото» (`photosChanged`).
- Сопоставление — по имени (`normalizeName`: регистр, лишние пробелы, ё→е), при совпадении
  сохраняется `id` — ссылки в старых КП не ломаются. Всё остальное (имя, должность,
  телефон, email, резюме, фото) перезаписывается сайтом: ручные правки этих полей не
  переживают синк.
- Пустое значение с сайта не затирает заполненное у нас (скорее всего это дырка в данных
  сайта, а не «контакт удалили»); то же с фото — не скачалось, остаётся прежнее. Если блок
  не найден — ошибка «изменилась вёрстка», справочник не трогается.
- **Предпросмотр — модалка, и это не украшательство.** Кнопка «Забрать с qmedia.by» стоит
  под списком из десятка карточек, а панель плана рендерилась в начале секции — при клике
  она уезжала за верхний край экрана (замерено: `top: -544px`), и пользователь видел, что
  «ничего не произошло», а данные не обновились. Туда же уезжали бы сообщения об успехе и
  ошибке, поэтому ошибки синхронизации живут в отдельном состоянии `syncError` и
  показываются внутри модалки, а после применения страница скроллится наверх, к итогу.
- Тесты — `__tests__/qmedia-managers.test.ts` (фикстура повторяет реальную разметку).

Как это доходит до расчёта:

- **Правка настроек не меняет уже сохранённые КП.** При сохранении КП в него кладётся снимок
  `Proposal.calcConfig`; PDF/Excel считают именно по нему (`mergeCalcConfig(proposal.calcConfig)`),
  у старых КП поля нет → `DEFAULT_CALC_CONFIG`. Пересчитать старое КП по новым настройкам =
  импортировать его JSON заново (импорт всегда берёт текущие настройки).
- **Тексты работ фиксируются копированием**, а не снимком настроек: `Wizard.initDirections`
  переносит строки каталога в `DirectionSelection.works`, дальше КП живёт со своей копией
  (PDF и Excel читают только `proposal.directions[].works` и в каталог не заглядывают).
  Поэтому отдельного `Proposal.worksConfig` нет и не нужно, а импорт JSON сохраняет тексты
  из файла — пересчёт по текущим настройкам касается только цен.
- Клиентские компоненты (`CostPanel`, `StepReview`) настройки **не запрашивают** — получают
  `config` пропсом от серверной страницы; сервер при сохранении применяет свою копию.
  Так же и каталог работ: `Wizard` берёт его пропсом (`works`) и один раз фиксирует в
  состоянии (`useState(() => buildWorksCatalog(works))`), `StepDirections` получает готовый
  `catalog` — правка настроек в соседней вкладке не перетасует уже размеченные работы.
- Формы держат числа **строками** (`CalcDraft` в `SettingsCalc.tsx`), иначе не набрать «1,»;
  в числа они превращаются при сохранении, там же собираются ошибки. Валидация на сервере —
  `calcConfigSchema` (zod, `lib/validation.ts`), затем `mergeCalcConfig` для канонизации.
- Через интерфейс **не** меняются: валюта (BYN), варианты срока (3/6), списки опций, названия
  и порядок направлений, правила округления — они завязаны на типы и вёрстку.

### Два менеджера в КП

В КП два человека, и выбираются они **независимо** — на практике КП готовит продавец,
а проект ведёт другой человек:

- `Proposal.manager` — кто подготовил КП. Обложка PDF («Подготовлено:») и Excel.
- `Proposal.projectManager` — кто ведёт проект. Свой слайд PDF + аватарка в строке
  «Project-менеджер» на слайде «Профильная команда».

Оба — шаг визарда на одном и том же компоненте `StepManager` (пропсы `title`/`hint`):
выбор из справочника или ручной ввод; поля можно поправить «только для этого КП» —
тогда КП отвязывается от справочника (`id` сбрасывается, а с ним и фото). Пустое имя =
«не указывать», тогда PDF/Excel подставляют `COMPANY.manager`.

`ProposalManager` кроме контактов несёт `resumeUrl` (ссылка «Смотреть резюме», снимок)
и **необязательный `id`** — он нужен ровно для одного: найти фото в `manager_photos`
при рендере PDF (см. «Фото менеджеров»).

## Доменная логика (расчёт)

- База `750`, час `75` BYN — это **значения по умолчанию**; фактические берутся из `CalcConfig`
  (третий аргумент `calculate`/`calculateSchedule`). Цена направления/мес =
  `base × коэф.направления × Π(применимые коэф.)`; часы = `round(цена / час)`.
- **Все стоимости кратны ставке часа** (`quantizePrice` в lib/calc.ts, правка заказчика от
  20.08.2026): цена = `round(сырая цена / ставка) × ставка`, поэтому `часы × ставка === цена`
  и в КП не бывает строк вроде «19 нч — 1 398 BYN» (должно быть 1 425). Округление — к
  ближайшему кратному, тем же ROUND, что и часы; включённое направление не схлопывается
  в ноль (минимум час). Приводятся **обе** цены — полная и со скидкой (скидка от кратной
  цены кратной не остаётся: `1275 × 0.7 = 892.5`), поэтому суммы, итоги и экономия тоже
  кратны ставке. `directionMonthlyPrice` при этом остался «сырой» формулой Excel — на нём
  держится золотой тест, кратность накидывает уже `calculate`.
- Наборы коэффициентов **различаются** по направлениям (см. `DIRECTION_COEFFICIENTS`):
  Коммерческое/GEO — все; Информационное/SERM — без страниц/ошибок/конкуренции;
  Техподдержка — только страницы/ошибки/опыт.
- Итог/мес = сумма включённых.
- **Помесячный состав** (главное отличие от Excel-исходника). Направление активно не на весь срок,
  а в произвольный набор месяцев: `DirectionSelection.activeMonths: number[]` (1-based; `[]` = не
  входит). «Включено» = `activeMonths.length > 0`. Срок остаётся 3/6 мес.
  - `calculate(input, directions)` (lib/calc.ts) — **неизменное ядро одного месяца** (на нём держится
    золотой тест). `calculateSchedule(input, directions)` — надстройка: для каждого месяца строит срез
    активных направлений и зовёт `calculate`, затем суммирует. Возвращает `ScheduleResult`
    (`months: MonthBreakdown[]`, `perDirection: DirectionScheduleCalc[]` с `activeMonths`/`monthsLabel`/
    `pricePerMonth`/`fullPricePerMonth`/`hoursPerMonth`/`totalPrice`, грандтоталы). Итог за срок =
    **сумма помесячных**, а не месяц × срок. `*PerMonth` — значения по активным месяцам (могут
    различаться: скидка действует только в месяцы с Коммерческим), из них PDF берёт цифры «в месяц».
  - `Proposal.calcSnapshot` теперь `ScheduleResult`. Все потребители (CostPanel, StepReview, PDF, Excel,
    storage) считают через `calculateSchedule`.
  - **Обратная совместимость**: старые КП в БД хранят `included: boolean` без `activeMonths`.
    `normalizeActiveMonths` (lib/calc.ts) приводит к `activeMonths` (`included:true` → все месяцы), а
    `validation.ts` принимает оба поля. Поэтому рендер старых JSON безопасен.
  - UI ввода — матрица «направления × месяцы» в `StepDirections`; смена срока ремапит `activeMonths`
    (`Wizard.remapMonths`). Подпись месяцев — `formatMonthRanges` (lib/format.ts).
- **Пакетная скидка** (`config.bundle`, дефолт — `COMMERCIAL_BUNDLE` в `seo-config.ts`): если
  включено **Коммерческое SEO**, то включённые **GEO и SERM** считаются со скидкой **30%** (`monthlyPrice` =
  `quantizePrice(fullMonthlyPrice × 0.7)`; часы — от цены со скидкой). Применяется **помесячно**: в месяце,
  где активно Коммерческое, активные GEO/SERM этого месяца идут со скидкой, иначе — по полной (это
  выходит само за счёт `calculateSchedule`, вызывающего `calculate` помесячно). В `DirectionCalc` есть
  `fullMonthlyPrice`/`discountRate`, в `ScheduleResult` — `totalFullPrice`/`totalDiscount`.
  Скидку показываем всюду: CostPanel, StepReview, PDF (смета + слайд работ направления; в PDF —
  помесячно, см. «Структура PDF»), Excel (колонки «Полная цена за срок» и «Скидка за срок»).
  Нет в исходном Excel — это бизнес-правило.
- **Золотой тест** (значения из кэша Excel — это **полные** цены до скидок): Вся РБ, b2b, до 1000,
  Единичные, Сайт продвигался, Базово, Средняя → «сырые» `1525/1155/1307/825/540` (их отдаёт
  `directionMonthlyPrice`), после приведения к кратности ставки — `1500/1125/1275/825/525`,
  сумма полных **5250 BYN**, часы те же, что в Excel (20/15/17/11/7). С пакетной скидкой
  (Коммерческое включено) GEO→`900`, SERM→`600`, итог/мес = **4650 BYN / 62 ч**, скидка
  **600 BYN**. Считается по дефолтному конфигу (тест зовёт `calculate`
  без третьего аргумента) — так и должно остаться. Любая правка расчёта обязана оставлять
  `npm test` зелёным. Тесты `calculateSchedule`/`formatMonthRanges` — там же, а
  `__tests__/calc-config.test.ts` проверяет `mergeCalcConfig` и расчёт по изменённым настройкам.

## Принятые решения и допущения

- Валюта **BYN**. Срок 3/6 мес. Итог за срок = **сумма помесячных** итогов (см. `calculateSchedule`),
  т.к. набор направлений может различаться по месяцам (раньше было месяц × срок).
- «Ссылочное продвижение» и «Конкуренция» — поля формы (есть в Excel, не было в ТЗ).
- «Что продвигаем» **не влияет** на цену (нет коэффициента) — только текст в КП.
- «до 500» страниц в Excel **отсутствует** → коэффициент `1.1` (допущение, правится в настройках).
- Авторизации нет (MVP, внутренний инструмент) — настройки открыты всем, кто дошёл до `/settings`.
- Сохранённое КП — **неизменяемый снимок**: и расчёт (`calcSnapshot`), и настройки
  (`calcConfig`), и менеджеры (`manager`, `projectManager`), и тексты работ
  (`directions[].works`). Пересчёт по новым настройкам — только через импорт JSON (и он
  меняет цены, а не формулировки работ). **Единственное исключение — фото менеджеров**:
  они хранятся ссылкой по `id`, см. «Фото менеджеров».
- **Оформление PDF — по макетам дизайнера** (`sources/cp-seo-deck.pdf`, 36 слайдов,
  19.08.2026). Правки заказчика к макетам: «Подготовил(а):» → «Подготовлено:» (чтобы не
  склонять по родам), небольшие скругления углов вместо остроугольных элементов, а слайд
  Project-менеджера упрощён — без «видеовизитки» и без списка личных достижений.
  Тексты слайдов настройками **не правятся** — только в коде (`lib/pitch.ts`).
- **Разбор вёрстки на Verdana (20.08.2026, после смены шрифта).** Сделано: заголовок
  «SEO… на рост заявок» ужат до 24 pt, чтобы шёл в две строки (в 27 pt первая строка
  в Verdana не помещалась в 668 pt); междустрочие заголовков ужато с `0.19` до `0.05`
  кегля (`HEAD_LINE_GAP_RATIO`) — высоту строки и так задаёт геометрия плашки; «!» на
  слайде «по старинке» крупнее текста и выровнен `alignCapTop`; приставка «от» на жёлтых
  плашках мельче суммы; «от 30 000 $» и «==передовые решения:==» — каждое в одну строку
  (под второе расширена левая колонка слайда «Гарантии»); вертикальные поля баннера
  состава работ выровнены по факту (было 5.9 pt сверху против 11.2 pt снизу); вывод
  слайда «почему дешевле» отлеплен от подвала. Освободившееся от заголовков место
  роздано обратно отступам — иначе низ листов пустовал.
- **Шрифт PDF — Verdana** (20.08.2026): заказчик принёс лицензионные файлы, «у нас в
  компании все PDF-презентации на этом шрифте». Это и шрифт исходных макетов, так что
  колода вернулась к тому, в чём её рисовали. Веб-интерфейс намеренно оставлен на
  PT Sans: там шрифт ни с чем не сверяется, а тянуть проприетарный файл в браузер
  посетителя — лишнее. Цена решения — подрезанные кегли и отступы на 15 листах
  (см. «Смена шрифта и пагинация»).
- **Разбор вёрстки от 20.08.2026** (заказчик прошёлся по готовому PDF). Сделано:
  водяные знаки вектором и заметнее, контакты в подвале крупнее и светлее, жёлтое
  кольцо аватара по кругу, прямые углы у фоторамок, серые логотипы клиентов и соцсетей
  (перекрашены сами файлы, см. «Конвенции»), скрепка на «Профильной команде» убрана,
  вывод слайда Project-менеджера — жёлтая плашка во всю ширину, крупные цифры на
  «Что мы ожидаем» прячутся под текстом, жёлтое выделение куска фразы переехало на
  настоящую плашку с симметричным воздухом (см. «Жёлтое выделение куска фразы»).
  Плюс сквозные требования: типографские переносы (см. «Типографика») и разрежённая
  вёрстка — свободное место внизу листов роздано отступам и кеглям.

## Грабли и уроки (важно!)

- **`@react-pdf/renderer` + Next: динамические узлы (`render`-проп) не выводятся.** Номера
  страниц через `render={({pageNumber})=>...}` не рендерятся (молча, ничего не видно).
  Поэтому подвал статический. Подробности и путь к фиксу — в памяти проекта
  `react-pdf-dynamic-nodes-next.md`. Не чинить позиционированием — дело не в нём.
- **Шрифт PDF — Verdana** (`public/fonts/Verdana*.ttf`, версии 5.03/5.05, с кириллицей),
  регистрируется в `lib/pdf/theme.ts`. Тот же шрифт, что в макетах дизайнера и в
  остальных презентациях Qmedia. Четыре начертания: Regular, Bold, **Italic и
  BoldItalic** — курсив react-pdf **не синтезирует**, без файла начертания рендер падает
  с «Could not resolve font», а в макетах курсив встречается часто (подписи фактов,
  формат отчётности, описания сервисов). У шрифта **нет** глифа `→` — заменять на тире
  через хелпер `clean()`; нет и `✓`/`✗` — рисовать `<Svg><Path>` или кружком-`View`.
  - **🛑 Файл обычного начертания — `Verdana.ttf`, без суффикса `-Regular`.**
  - **До 20.08.2026 в PDF был PT Sans** (OFL) под именем QmediaSans — свободная замена,
    пока лицензионных файлов Verdana не было. Веб-интерфейс на нём и остался
    (`@font-face` в `globals.css`), файлы `QmediaSans-*.ttf` из `public/fonts` удалять
    нельзя.
  - **🛑 Verdana заметно шире PT Sans:** одна и та же строка занимает на ~20% больше
    места в обычном начертании и на ~33% — в жирном (замер по строкам колоды через
    `fontkit`). При переезде из-за этого разъехалось 15 листов из 31; кегли и отступы
    подрезаны обратно (см. «Смена шрифта и пагинация»).
  - **Метрики шрифта живут в `theme.ts` двумя числами** — `ASCENT_RATIO` (`hhea.ascent`)
    и `CAP_RATIO` (`OS/2.capHeight`), обе в долях `unitsPerEm`. Из них считаются
    `CAP_TOP_RATIO`, `GLYPH_SINK_RATIO` и `plateText`. Меняешь шрифт — меняй эти два
    числа, остальная оптика пересчитается сама.
- **`marginTop: "auto"` в react-pdf ненадёжен.** Чтобы прижать блок к низу листа, ставить
  распорку `<View style={{ flexGrow: 1 }} />` перед ним.
- **Текст в цветной плашке НЕ центрируется сам.** При `lineHeight: 1` react-pdf сажает
  базовую линию почти на низ строчного бокса, поэтому глиф оказывается ниже центра плашки
  на `GLYPH_SINK_RATIO × кегль` (для Verdana ≈0.141, у прежнего PT Sans было ≈0.164).
  Коэффициент **не подбирается**, а считается из метрик шрифта:
  `CAP_TOP_RATIO + CAP_RATIO / 2 − 0.5`, то есть насколько центр полосы прописных ниже
  центра коробки. Не «поправлять на глаз», а брать хелперы
  `lib/pdf/theme.ts`: `opticalCenter(fs)` — для flex-центрирования, `platePadding(fs, pad)` —
  для плашки на паддингах (жёлтые хайлайты, плашки сумм, бейджи срока; высоту не меняет),
  `centerTextTop(h, fs)` — для абсолютной строки (телефон и почта в подвале).
  **Хелперы работают только вместе с `lineHeight: 1`** — при унаследованном 1.4 глиф, наоборот,
  встаёт чуть ВЫШЕ центра, и поправка удваивает ошибку (наступали: бейдж уехал на −3pt).
- **Разный кегль в одном флекс-ряду — через `alignCapTop(base, size)`.** Верх прописных
  отстоит от верха строчной коробки на `CAP_TOP_RATIO × кегль`, то есть у крупной ячейки
  больше; `alignItems` react-pdf на таком ряду игнорирует. Хелпер возвращает поправку
  `marginTop`. Так стоит крупный жёлтый «!» рядом со строкой вывода на слайде
  «по старинке».
- **В строке таблицы кегль всех ячеек должен совпадать.** `alignItems: "center"` и
  `"baseline"` на такой строке react-pdf **игнорирует** (проверено рендером — вывод
  побайтово тот же), а разный кегль даёт разную высоту строчного бокса и текст встаёт на
  разной высоте. Меняешь кегль в одной ячейке сметы — меняй во всех ячейках строки.
- **Как проверять выравнивание.** На глаз не видно: речь о долях пункта. Рендерить и мерить
  пиксели — `pdftoppm -r 600` в PPM (формат P6 парсится в 10 строк), заливкой найти цветную
  плашку и сравнить её центр с bbox текста. Важно: **ink-bbox — не то же, что оптический
  центр.** Выносные элементы (запятая в «9 150,00», «р» в «Направление», «/») тянут bbox
  вниз и дают ложное «смещено» на 1–2pt; скруглённые углы плашки подмешивают фон. Сверять
  надо **верх литер** — если он совпал, базовые линии совпали.
- **react-pdf: крупный `fontSize` + унаследованный `lineHeight` 1.4 → текст налезает на
  соседний.** Для больших чисел/заголовков ставить `lineHeight: 1` + `marginBottom`.
- **Абсолютный элемент только с `right` схлопывает ширину** (текст не виден). Задавать
  `left` + `right` + `textAlign`.
- **🛑 react-pdf ВЕШАЕТ раскладку (синхронный бесконечный цикл), если абсолютная `<Image>`
  с отрицательным смещением / выходящая за край лежит прямо в `<Page>`.** Симптом: рендер
  висит вечно, vitest не показывает даже таймаута теста (event loop заблокирован). Лечение:
  оборачивать такие watermark-картинки в контейнер с `overflow:"hidden"` (примитивы
  `Watermark`/`Overlay`). Диагностика — бисекция через esbuild-бандл
  + `execFileSync(..., {timeout})` (vitest тут бесполезен — воркер виснет молча).
- **🛑 `<Page wrap={false}>` — это НЕ «обрезать по листу», а «подогнать высоту листа под
  контент».** Страница перестаёт быть 720×405, и КП разъезжается по разным форматам
  (ловилось так: `pdfinfo` показывал 365 / 295 / 416 pt вместо 405). Лист, в который
  контент не влез, должен честно распасться на два — это видно на визуальной проверке.
- **🛑 Абсолютный блок, выходящий за нижнюю границу контентной области, вешает пагинацию.**
  Движок бесконечно пытается перенести его на следующий лист (симптом тот же, что и у
  watermark-картинки: рендер висит вечно). Лечение — примитив `Overlay`: слой во весь лист
  с `fixed` (выводит из потока пагинации) и `overflow: "hidden"`. Через него идут воронка
  «путь клиента» и все водяные знаки.
- **🛑 Слово с переходом латиница→кириллица react-pdf рвёт и дописывает лишний дефис:**
  «AI-поиск» → «AI--поиск», «SEO-поддержка» → «SEO--поддержка», «Project-менеджер» → …
  Причина: `scriptItemizer` (@react-pdf/textkit) режет строку на runs по юникод-скрипту
  **до** переноса слов, `wrapWords` собирает «слоги» внутри каждого run, между соседними
  непробельными слогами кладётся penalty-узел, и `breakLines` при переносе **безусловно**
  дописывает дефис. Кегль, ширина и `hyphenationPenalty` не спасают (проверено: до 5000
  раскладку не меняет, 9999+ ломает её — текст пропадает).
  Лечение — колбэк переносов в `theme.ts`: после каждого куска, кончающегося дефисом,
  возвращаем **пустой слог**. Пустая строка проходит проверку `s.trim() === ''` и
  становится glue-узлом нулевой ширины: точка переноса остаётся, penalty-узла (и лишнего
  дефиса) больше нет. Бонусом переносятся и чисто кириллические слова через дефис
  («интернет-маркетинг»), которые раньше просто вылезали за край блока.
- **Перевод строки внутри одного `<Text>` — это новый абзац**, и react-pdf подмешивает
  в лист неиспользуемый `Helvetica` (виден в `pdffonts`). Многострочные заголовки и
  заметки собирать **отдельными `<Text>`**, а не `"строка\nстрока"`.
- **Dev-сервер Next кэширует модули PDF агрессивно.** После правок в `lib/pdf/*` первый
  запрос может отдать старую сборку, а изредка — «полусобранную» (наблюдалось: у строки
  пропали первые символы, `example.by` → `xample.by`). Если рендер выглядит странно —
  `make restart` и перепроверить; в чистом рендере (`renderToFile` из скрипта) этого нет.
- **`Buffer` → `Response`.** TS ругается на `BodyInit`; оборачивать в `new Uint8Array(buffer)`.
- **Бутстрап.** Папка не пустая (`sources/`) — `create-next-app` откажется; проект собран
  конфигами вручную.
- **Хранилище — Postgres, не файлы.** Раньше КП лежали в `data/proposals/*.json`; на serverless
  (Vercel) ФС эфемерна и данные терялись бы. Теперь — таблица `proposals` в Postgres
  (Neon/Supabase), `data jsonb`. На Vercel в `DATABASE_URL` класть **pooled/pooler** строку
  подключения (иначе можно упереться в лимит коннектов). Колонка `id` — `text` (id всегда из
  `crypto.randomUUID`), чтобы не ловить ошибки каста `uuid` на «мусорных» id. Настройки — там же,
  в `app_settings` (ключ → jsonb); схему и разовые правки данных накатывает `lib/migrations.ts`
  через `ensureSchema()` (см. «Миграции»).
- **JSON из БД нельзя типизировать «на веру».** Настройки и снимок `Proposal.calcConfig` —
  произвольный jsonb (может быть от старой версии или поправленным руками), поэтому читаются
  только через `mergeCalcConfig` / `normalizeManagers`: недостающее берётся из дефолтов,
  мусор отбрасывается. `Proposal.calcConfig` намеренно объявлен `unknown` — чтобы это нельзя
  было обойти и чтобы `types.ts` не зависел от `calc-config.ts`.
- Тяжёлые пакеты (`@react-pdf/renderer`, `exceljs`) вынесены во внешние через
  `serverComponentsExternalPackages` в `next.config.mjs`.

## Конвенции

- **Бренд green-forward.** Основной цвет — зелёный `#53BD35`, акцент — жёлтый `#FFDE00`
  (сверены с CSS qmedia.by). Чёрный почти не используется (только тёмный текст). Палитра
  в `BRAND` (`lib/company.ts`) и `tailwind.config.ts` зеркальны. Логотипы — `public/brand/logo-*.svg`
  (в вебе SVG; в PDF — белые PNG, т.к. react-pdf не грузит SVG через `<Image>`).
- **Жёлтый — только подложка или мелкая графика, никогда не текст:** `#FFDE00` на белом
  нечитаем. В PDF он работает ровно так же, как в макетах: плашка за строкой (подпись под
  заголовком слайда, `==разметка==` внутри фразы, имя менеджера, названия ролей команды),
  плашка суммы, кнопки-таблетки, рамки картинок (награды, отзывы, кейсы, карта) и бейдж
  срока направления. Текст на жёлтом — всегда чёрный.
- **Палитра PDF — `DECK` в `lib/pdf/theme.ts`**, не `BRAND`. Зелёный и жёлтый совпадают,
  остальное — оттенки дизайнера, которые нигде, кроме PDF, не используются: `note`
  (`#A8D08C`, плашка-вывод), `fact` (`#D9EAD3`, плашка-факт и баннеры), `bullet`
  (`#A1E090`, маркер списка), `card` (`#F3F3F3`), `cardLine` (`#E7E6E6`),
  `watermark` (`#F5F5F5`, знак «Q» на белом листе), `footerText` (`#EAF6E3`, контакты
  на зелёном). В `BRAND` и `tailwind.config.ts` их не тащим — зеркальность этой пары
  про веб-интерфейс.
- **Монохромную графику красим в файле, а не в коде:** react-pdf не умеет тонировать
  `<Image>`. Иконки соцсетей и логотипы клиентов приехали из презентации чёрными
  вперемешку с серыми — перекрашены в один серый (`#9E9E9E`) прямо в PNG. `opacity`
  вместо этого не годится: она осветляет и белые детали внутри знака (глиф TikTok,
  «МТС» в плашке).
- **Общение с пользователем — только на русском** (техн. идентификаторы как есть).
- Литералы значений в типах/конфиге совпадают со значениями Excel — чтобы выгрузка и расчёт
  были зеркальны исходнику. Не переименовывать без необходимости.
